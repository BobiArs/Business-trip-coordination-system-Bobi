# Екзаменаційний проект: «Система узгодження відряджень» (Варіант 2)

## 📌 Бізнес-сценарій
Компанія регулярно відправляє співробітників у відрядження для участі у зустрічах із клієнтами, внутрішніх заходах, навчанні та переговорах із партнерами.
* **Співробітник** повинен мати можливість створити заявку на відрядження, вказати мету поїздки, дати, напрямок, рівень терміновості та контактні дані, а потім відстежувати поточний статус її узгодження.
* **Менеджер** працює у внутрішньому інтерфейсі компанії, де він бачить список заявок, переглядає картку заявки, змінює статус, додає коментарі та контролює процес узгодження.
* **Керівник** очікує отримати сучасний SPA-додаток зі зручною навігацією, безпечним доступом, коректною роботою з API та зрозумілою модульною архітектурою.

---

## 🎯 Основне завдання проекту
Спроектувати та реалізувати клієнтський веб-додаток на **React** та **TypeScript** для роботи із заявками на відрядження.

Результатом має бути SPA-додаток, у якому реалізовано:
* Авторизацію з розподілом ролей (Співробітник / Менеджер).
* Створення та перегляд заявок на відрядження співробітником.
* Узгодження, коментування та зміну статусів заявок менеджером.
* Маршрутизацію (захищені роути), форми з валідацією, роботу з серверним станом та інтеграційне тестування.

## 🖥️ Джерело серверних даних та Mock API

> [!IMPORTANT]
> Backend-частину програми студент **не розробляє**. Усі серверні запити мають перехоплюватися у браузері за допомогою бібліотеки **MSW (Mock Service Worker)**.

* **Перехоплення запитів**: Під час роботи програми у браузері MSW перехоплює HTTP-запити. Під час тестування використовуються ті самі обробники (handlers) через `msw/node`.
* **Динаміка даних**: Mock API повинен містити змінювані дані про користувачів, заявки на відрядження, коментарі менеджерів та історію статусів. Створені або змінені дані мають зберігатися в межах поточного сеансу (збереження після повного перезавантаження сторінки через F5 не є обов'язковим).
* **Стек для мережі**: Взаємодія з mock API має здійснюватися за допомогою **Axios** та **TanStack Query**.

### 🔐 Тестові облікові записи
* **Співробітник**: `employee@example.com` / пароль: `employee123`
* **Менеджер**: `manager@example.com` / пароль: `manager123`

### Список обов'язкових сутностей для моделювання:
1. Користувачі (з різними ролями)
2. Заявки на відрядження
3. Категорії цілей поїздки (напрямки діяльності)
4. Рівні терміновості
5. Статуси заявок на відрядження

### 🗄️ Вимоги до початкового набору даних (Initial Seed):

| :--- | :--- | :--- |
| **Користувачі** | $\ge 2$ | Різні ролі (employee та manager) |
| **Заявки на відрядження**| $\ge 5$ | Присутні різні статуси та різні рівні терміновості |
| **Категорії цілей** | $\ge 3$ | Наприклад: *Зустріч з клієнтом*, *Навчання/Конференція*, *Переговори з партнерами* |

| **Статуси заявок** | $\ge 4$ | Наприклад: *Чернетка/Нова*, *На розгляді*, *Затверджено*, *Відхилено* |
| **Коментарі менеджерів**| $\ge 2$ | Пов'язані з тестовими заявками на відрядження |
| **Історія статусів** | $\ge 2$ | Записи про хід узгодження |

## 🔌 Обов'язкові Endpoints Mock API

Всі захищені ендпоінти повинні перевіряти наявність правильного заголовка `Authorization: Bearer <token>`. За його відсутності або недійсності повертати помилку **401 Unauthorized**.

| Метод | Шлях | Опис | Захищений |
| :--- | :--- | :--- | :--- |
| **POST** | `/auth/login` | Вхід у систему, повертає JWT-токен та роль | Ні |
| **GET** | `/auth/me` | Отримання даних поточного авторизованого користувача | Так |
| **GET** | `/business-trips/my` | Список заявок поточного співробітника (для ролі `employee`) | Так |
| **GET** | `/business-trips` | Загальний список заявок компанії (для ролі `manager`) | Так |
| **GET** | `/business-trips/:id` | Детальна картка конкретної заявки за її ID | Так |
| **POST** | `/business-trips` | Створення нової заявки на відрядження співробітником | Так |
| **PATCH**| `/business-trips/:id/status`| Зміна статусу заявки (узгодження) менеджером | Так |
| **POST** | `/business-trips/:id/comments`| Додавання коментаря менеджером | Так |
| **GET** | `/business-trips/:id/history`| Отримання історії зміни статусів для заявки | Так |
| **GET** | `/trip-purposes` | Отримання списку категорій цілей поїздки | Так |
| **GET** | `/urgency-levels` | Отримання списку рівнів терміновості | Так |
| **GET** | `/business-trip-statuses`| Отримання списку доступних статусів заявок | Так |

## 🛠️ Функціональні вимоги до програми

### 1. Аутентифікація та контроль доступу
- [ ] Вхід у систему через форму авторизації.
- [ ] Використання **React Hook Form** для побудови форми.
- [ ] Валідація полів на клієнті за допомогою бібліотеки **Zod**.
- [ ] Збереження `accessToken` та ролі користувача після успішного входу.
- [ ] Автоматичний запит профілю користувача через ендпоінт `GET /auth/me` після входу.
- [ ] Реалізація **захищених маршрутів (Protected Routes)**. Неавторизований користувач не може потрапити на внутрішні сторінки (перенаправлення на `/login`).
- [ ] Розподіл прав доступу:
  * Роль `employee` має доступ лише до створення заявок та перегляду списку своїх заявок.
  * Роль `manager` має доступ до загального списку та управління статусами/коментарями.
- [ ] Використання виділеного інстансу **Axios** (Axios instance) з додаванням токена в інтерсептори.
- [ ] Додавання **interceptor для обробки помилок 401**. При отриманні 401 додаток повинен очистити локальні дані сесії та перенаправити користувача на `/login`.

### 2. Робота із заявками на відрядження
- [ ] Список доступних статусів для фільтрації та зміни статусу має завантажуватися динамічно з API.
- [ ] Створення заявки через окрему сторінку з формою (використовувати **React Hook Form** + **Zod**).
- [ ] Заявка обов'язково повинна містити: *ID, мету поїздки, опис, напрямок (місто/країну), дату початку, дату закінчення, рівень терміновості, дату створення, поточний статус* та *контактні дані співробітника*.
- [ ] Перегляд списку заявок (співробітник бачить лише свої, менеджер — усі).
- [ ] Перегляд детальної картки заявки за її ID (з відображенням історії зміни статусів та коментарів).
- [ ] Зміна статусу заявки (лише для менеджера).
- [ ] Додавання коментаря менеджером до заявки.
- [ ] Відображення помилок форм та стану надсилання даних (loading state для кнопок сабміту).
- [ ] Програмний редірект користувача на сторінку створеної заявки після її успішного додавання.

### 3. Маршрутизація та навігація
- [ ] Використання **React Router** для навігації.
- [ ] Окремі Layout-компоненти:
  * **Public Layout**: для гостьових сторінок (авторизація).
  * **App Layout**: для внутрішньої робочої зони (з навбаром, інформацією про користувача та кнопкою Logout).
- [ ] Обов'язкові маршрути:
  * `/login` — сторінка входу.
  * `/business-trips` — список заявок на відрядження.
  * `/business-trips/new` — створення заявки (лише для `employee`).
  * `/business-trips/:id` — картка заявки (динамічний параметр).
  * `/not-found` — сторінка 404 (всі невідомі роути перенаправляються сюди).
- [ ] Використання **Search Params** (рядок запиту URL) для фільтрації списку заявок за статусом.
- [ ] Переходи між екранами здійснюються виключно через `<Link>` або `<NavLink>` (без перезавантаження сторінки).
- [ ] Програмне перенаправлення після успішного входу залежно від ролі:
  * `employee` $\rightarrow$ `/business-trips` (бачить лише власні заявки).
  * `manager` $\rightarrow$ `/business-trips` (бачить загальний список).

### 4. Робота з Server State (TanStack Query)
- [ ] Читання даних через хук `useQuery`.
- [ ] Зміна та надсилання даних (POST/PATCH) через хук `useMutation`.
- [ ] Інвалідація та оновлення стейту (refetching) після успішних мутацій:
  * Створення заявки $\rightarrow$ оновлення списку.
  * Зміна статусу або додавання коментаря $\rightarrow$ оновлення детальної картки та історії статусів.
- [ ] Обробка станів інтерфейсу для екрану списку: **Loading**, **Error**, **Empty** (когда немає заявок) та **Success**.
- [ ] Обробка станів для картки заявки: **Loading**, **Error**, **Success**.
- [ ] Обов'язкова типізація всіх **DTO (Data Transfer Objects)** для запитів та відповідей.
- [ ] Чітке розділення клієнтського стану (наприклад, стан відкриття модального вікна) та серверного стану (дані заявок з кешу TanStack Query).
- [ ] **Штучна затримка**: у Mock API має бути додано `delay` щонайменше **800 мс** для ендпоінту списку заявок (для демонстрації skeleton/spinner).
- [ ] **Симуляція помилок**:
  * Сценарій повернення помилки **500 Internal Server Error** для демонстрації обробки серверних збоїв.
  * Сценарій **Network Error** (помилка мережі) для перевірки реакції інтерфейсу.

### 5. Стан програми та інтерфейс (UX/UI)
- [ ] Використання `useRef` для встановлення автофокусу в перше поле (Email) форми авторизації при завантаженні сторінки.
- [ ] Використання **Context API** для глобального UI-стану.
- [ ] Через Context API необхідно реалізувати систему спливаючих повідомлень (**Toast Notifications**) про успішні чи неуспішні дії (успішний вхід, помилка входу, створення заявки, зміна статусу тощо).
- [ ] Реалізація імутабельного оновлення стану в коді (наприклад, при фільтрації чи локальному оновленні даних).
- [ ] Коректна реакція інтерфейсу на помилки: виведення зрозумілих повідомлень користувачу замість «сирих» помилок консолі.

## 📐 Архітектура та якість коду

### 🏛️ Feature-Sliced Design (FSD) Lite
Структура проекту має відповідати методології FSD з явно виділеними шарами:
* `src/app/` — ініціалізація додатка (провайдери, стилі, маршрутизатор).
* `src/pages/` — сторінки додатка (композиція віджетів та фіч).
* `src/widgets/` — великі самостійні блоки інтерфейсу (наприклад, Header, Sidebar).
* `src/features/` — дії користувача, які приносять бізнес-цінність (наприклад, `auth-by-email`, `approve-trip`, `add-manager-comment`).
* `src/entities/` — бізнес-сутності додатка, їхні типи та UI-картки (наприклад, `trip`, `user`).
* `src/shared/` — перевикористовувані ресурси (компоненти UI, хелпери, axios instance, контект повідомлень).

### ⚡ Оптимізація
- [ ] Реалізувати ліниве завантаження (**Lazy Loading**) для сторінки детального перегляду заявки `/business-trips/:id` за допомогою `React.lazy()` та `Suspense`.

## 🧪 Тестування

Необхідно написати щонайменше **2 інтеграційні тести** з використанням **Vitest** та **React Testing Library**:
1. **Тест 1**: Перевірка успішного входу співробітника (імітація заповнення форми, натискання кнопки та перевірка перенаправлення/появи профілю).
2. **Тест 2**: Перевірка відображення повідомлення про помилку у разі виникнення помилки 500 або Network Error від сервера.

> [!WARNING]
> Для перехоплення запитів у тестах повинні використовуватися ті самі обробники (handlers) MSW, що й у самому додатку, підключені через `msw/node`.
